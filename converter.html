Converting a share link to a Clash config

A share link names a node. A Clash config tells the kernel what to do with it. The distance between the two is short, and every conversion bug lives inside it.

Three groups a share link carries

Whatever the scheme — vmess://, vless://, trojan://, ss://, hysteria2:// — it packs the same three groups, in a different order and often in a different encoding.

GroupWhat it isWhere it hides
IdentityUUID or password proving the node may be useduserinfo before @, or a field inside a base64 JSON body
TransportTCP or QUIC, plain or WebSocket, with path and Hostquery parameters, or net / type inside the encoded body
TrustTLS server name, certificate policy, REALITY keyssni, allowInsecure, pbk / sid / fp

A Clash proxy entry splits the same three groups into server and port, a transport block (ws-opts, grpc-opts, reality-opts) and a TLS block (tls, servername, skip-cert-verify, client-fingerprint). Conversion is that regrouping. Nothing gets added, and nothing should be dropped — so a config that imports cleanly but carries no traffic almost always lost something here.

The four regroupings that fail silently

1. ss: deciding where the base64 ends

SIP002 encodes only the credential — ss://base64(method:password)@host:port — while the older form encodes the whole body, ss://base64(method:password@host:port). Both are accepted in the wild. Split the second one on @ and the server address becomes garbage, but the parser still yields a structurally valid type: ss entry, so nothing complains until the connection times out.

2. vmess: a cipher the kernel does not accept

vmess:// is base64 over a JSON object, and scy holds the cipher. Clash accepts auto, aes-128-gcm, chacha20-poly1305 and none. Anything else has to be normalised on the way in. Skipping that step produces a config the core rejects at load time with a message about the proxy type, not about the cipher.

3. vless: a kernel that never supported it

vless has no password; identity is the UUID in the userinfo position. The original Clash core has no vless support at all, so converting vless to a Clash config only works on Clash Meta or mihomo. On the older core the node imports, shows as available, and never carries a byte.

4. REALITY: dropping the keys that make the handshake work

security=reality carries three values that have no equivalent anywhere else: pbk becomes public-key, sid becomes short-id, and fp becomes client-fingerprint. flow=xtls-rprx-vision copies across verbatim. Lose any one of them and the node authenticates but the tunnel never passes traffic — the failure looks like a dead server, not a bad config.

Check the result in three steps

Parse first: load the YAML and confirm the proxies: list has the expected number of entries. Then confirm the client actually selected one of them — a proxy group with no selection is a valid config that routes nothing. Last, confirm the exit changed: the egress address after enabling the profile should differ from the one before it. Skipping the third step is how a config that silently fell back to direct gets mistaken for a working one.

If you would rather not paste links into a service

The conversion itself is mechanical, so it does not need a backend. Two browser-local converters, one per language, take a list of share links or a base64 subscription and emit a Clash YAML without uploading anything: vmess to Clash converter (English) and 订阅链接转换器（中文）. The field mapping the converter applies is written out on those pages so the result can be checked by hand.
